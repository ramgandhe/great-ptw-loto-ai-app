### S0b draft safeguards — 2026-10-01
- Offline permit queue (mobile): requests are queued exactly as the API takes them; the local permit a queued create makes is kept in its own column (local_ref), not in the body. A new permit made offline is one create with everything entered (revision 0); saves made after it queue against its local id and carry their revision (0, 1, …, counted from the saves still queued); a submit queues after them. On replay the create's server id is recorded (local_ids table, offline schema v4) and later requests are pointed at it; the local draft is removed once the server copy exists; links and the editor resolve a synced local id to the server permit.
- Replay rules (pure `replayQueue`/`prepareReplay`, tested): a request the server refuses (409 conflict, validation, access) is kept as failed with its reason and every later request for the same permit is held with it, so a submit never runs after the save it depended on failed; other permits carry on. Unreachable server or 5xx: stop in order and retry later (max attempts as before). Signed out: stop. Requests queued by older app versions: unknown keys (localDraftId, action) are removed and a legacy create keeps its local id; a save or submit without a revision is failed for review, never guessed.
- Settings and Platform sync panels list failed items with what they were ("New permit: …", "Permit changes", "Permit submission") and why; their input stays in the queue.
- Attachments (API): upload stores the file, then inserts the metadata in a transaction that locks the permit and re-checks it is editable; if that fails (for example a submit won the race) the stored file is removed. Remove deletes the metadata under the lock first and the stored file only after commit. Draft deletion now locks the permit, deletes it, and then removes its attachments' stored files (they were left in storage before). Attachments do not bump the draft revision: they are added and removed individually and draft saves never replace them, so an open editor is not forced into a conflict by an upload.
- Evidence: offline-replay.spec.ts (7 tests: create/save/submit replay in order against the new id; refused save holds its submit while another permit syncs; unreachable stops in order; legacy bodies cleaned; missing revision fails; unknown local id fails); permit-draft-revision.spec.ts adds two DB tests (submit winning between storage and metadata leaves nothing attached or stored; draft delete removes stored files); against the rebuilt local API: the old queued body is refused (400), the new create with every field gives revision 0 with its executor, a save at 0 succeeds, a stale save gets PERMIT_REVISION_CONFLICT; full Jest 123/123 suites (544 tests); mobile and API tsc pass.
