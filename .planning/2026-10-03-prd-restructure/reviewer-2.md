# Reviewer 2: technical architecture, multi-tenant security and data privacy

PRD: `docs/specs/2026-10-04-permitwiseai-v2-prd.md` v0.1. Codebase facts checked on branch `feat/mobile-ui-refresh`, 2026-10-04.

### R2-01 [blocker] Row-level security is bypassed by the database roles the stack uses
- Where: NFR-SEC-001, §18 Isolation, §22 R1
- Problem: Superusers, roles with BYPASSRLS, and table owners (unless FORCE ROW LEVEL SECURITY is set) skip every policy. Today the API (`docker-compose.yml:120`, `docker-compose.app.yml:17`), Keycloak (`KC_DB_URL` → `ptw_platform`) and Metabase (`MB_DB_DBNAME: ptw_platform`) all connect as `ptw`, the `POSTGRES_USER` superuser of the one application database. Deployed like that, NFR-SEC-001 would pass on paper and enforce nothing, and the Keycloak and Metabase tables sit in the schema that the "policy on every table" test has to cover.
- Change: Add after NFR-SEC-001:
  "NFR-SEC-001a The API and workers connect as a dedicated login role that is NOSUPERUSER and NOBYPASSRLS and owns no table. Migrations run as a separate owner role that the API cannot assume. Every table in the application schema has ENABLE and FORCE ROW LEVEL SECURITY and at least one policy. Global tables (industry library, plans, platform default workflow) have a read-all policy and only the platform role can write to them. The API role has only INSERT and SELECT on audit and access-log tables. Keycloak uses its own database and role. Any reporting tool (Metabase) is either removed or connects as a read-only role limited to views with no permit content or personal data. A CI schema test, run as the API role, fails if any application table lacks FORCE RLS or a policy, or if the API role is a superuser, has BYPASSRLS or owns a table."
  In §22 R1, replace the mitigation with "Mitigation: NFR-SEC-001a (API role that neither owns tables nor bypasses RLS; FORCE RLS; schema test run as the API role); isolation suite in CI." In §18 Stack, add "Metabase: removed, or restricted under NFR-SEC-001a."

### R2-02 [blocker] The RLS context is undefined for pooled connections, tenant switching, caches and background jobs
- Where: §18 Isolation and Identity, NFR-SEC-001, FR-ONB-016, FR-WFE-008, FR-PRV-009
- Problem: §18 says policies are "driven by session settings". On the API's shared `pg` Pool (Drizzle, `app/src/database/database.module.ts`), a session-level `SET` stays on the connection, so the next request inherits another tenant's context. The PRD never says how the active tenant is validated after a switch, how long the Redis permission cache may keep a revoked role or ended engagement working, or what context BullMQ jobs (escalations, retention deletion, billing usage, certificate warnings) run under; today jobs carry no tenant context, and failed jobs with their payloads are kept forever (`app/src/infrastructure/queue/queue.service.ts:42`, `removeOnFail: false`).
- Change: Replace the §18 "Isolation" paragraph with:
  "Isolation: every request and every job runs its queries in a transaction that first sets `app.tenant_id`, `app.person_id`, `app.legal_entity_ids` and `app.acting_role` with `set_config(name, value, true)`. These settings last only for that transaction. Session-level SET is forbidden, and a lint rule blocks it. Policies read the settings with `current_setting(name, true)` and return no rows when one is missing (default deny). Policies call STABLE helper functions over indexed columns."
  Add to §16:
  "NFR-SEC-006 The server chooses the active tenant from the account's verified memberships and engagements and keeps it in the server session. It is never taken from a client-supplied header or body alone. A tenant switch (FR-ONB-016) creates a new session context, and the browser or app clears data it cached for the previous tenant."
  "NFR-SEC-007 The permission cache is keyed by account and active tenant. Role edits, assignment changes, an engagement ending, offboarding and a support grant expiring each invalidate the affected entries immediately. As a backstop, no entry lives longer than 5 minutes."
  "NFR-SEC-008 Job payloads carry the tenant ID and record IDs only, never names, contact details or health data. The worker sets the same transaction-local context from the payload. Jobs that span tenants (timer sweeps, billing usage, retention deletion, trial expiry) get tenant IDs from a single SECURITY DEFINER function and then process each tenant under its own context; they never use a bypass role. Failed jobs are kept for at most 7 days. Result caches in Redis (dashboards, KPIs, reports) are keyed by tenant and by the viewer's legal-entity scope."
  Append to §21 criterion 4: "...; the suite also proves that a pooled connection reused after a tenant-A request returns no tenant-A rows to a tenant-B request, and that a job without tenant context reads nothing."

### R2-03 [blocker] Agency access cannot be enforced by "the same database rules" as written
- Where: NFR-SEC-002, FR-AGY-005, FR-AGY-006, FR-PRV-007, FR-ONB-015, FR-ONB-016, §18 Isolation
- Problem: RLS filters rows, not columns. A policy that lets a client user read an agency `people` row also returns the identity document, hire details, employment history and every other column that FR-AGY-006 forbids. The emergency subset is encrypted with the agency's data key (NFR-SEC-003), and the PRD never lets a client context use that key. It also never says which tenant an agency user's session runs in while working a client permit, so policies for "a person from tenant B acting on tenant A's rows" are undefined.
- Change: Replace NFR-SEC-002 with:
  "NFR-SEC-002 Data crosses tenants by exactly two paths, both enforced in the database. (a) Agency to client: an agency user's session tenant is always the agency (FR-ONB-015). The user can read client permits, and the plant and place names they reference, through a policy that needs an active engagement covering the permit's plant and the user's assignment to that permit (nominated receiver or crew member). Writes are limited to the step actions the user holds on that permit. (b) Client to agency staff: client sessions have no policy on the agency's people, certificate or insurance tables. They read agency staff only through one security-barrier view or SECURITY DEFINER function, which returns the FR-AGY-006 columns for people on that client's permits under an active engagement. Only the personal-data service returns the emergency subset decrypted, under FR-PRV-006 conditions and with the agency's data key, and it logs each view in the agency's access log and in the client's audit."
  In FR-ONB-016, replace "belongs to, or is engaged with, more than one tenant" with "holds person records in more than one tenant (FR-PPL-004)" and add: "Agency staff never switch into a client tenant; they see client permits from their agency tenant through NFR-SEC-002 (a)."
  Append to §21 criterion 4: "...; the suite includes a client user selecting every column of the agency staff tables directly and getting no rows."

### R2-04 [blocker] Consent, as specified, contradicts the people-creation flow and Indian and EU law
- Where: FR-PRV-001, FR-PRV-002, FR-ONB-009, FR-ONB-010, FR-PPL-003, §22 R4, D13
- Problem: The admin enters health data when creating or importing a person (FR-ONB-009, FR-PPL-003), but consent is asked only at first sign-in (FR-ONB-010). So the data is stored before consent, which contradicts FR-PRV-002, and crew who never sign in are never asked. Under GDPR, an employee's consent to the employer is rarely freely given (EDPB Guidelines 05/2020), and health data needs an Art. 9(2) condition. Under the DPDP Act 2023: employment and medical emergency are s.7 legitimate uses; withdrawal must be as easy as giving consent (s.6(4)), and the PRD has no withdrawal at all; and the notice and consent request must be available in English or an Eighth Schedule language (s.5(3), s.6(3)). D13 ("English only") leaves no room for that, which is a concrete legal conflict for this text only.
- Change: Replace FR-PRV-001 and FR-PRV-002 with:
  "FR-PRV-001 Each legal entity (or agency) records, for each data category (identity, contact, emergency contacts, blood group, health conditions, employment history, check-in location and photo), its purpose and lawful basis: legal obligation, employment, vital interest or medical emergency, or consent. The platform default for blood group, emergency contacts and health conditions is consent; an admin may change it only after recording the legal reason. The privacy notice and consent text are versioned, and each version may have translations. The person can read them in any language the legal entity provides. This is an exception to D13 for notice and consent text only."
  "FR-PRV-002 Data that relies on consent cannot be entered, imported or stored until the person has given consent, either in the app or on a signed paper form uploaded by the admin (version, date and method recorded). Spreadsheet import (FR-ONB-009) rejects those columns for people without a consent record. A person can withdraw consent at any time from their profile, as easily as they gave it. On withdrawal, the data that relies on it is deleted within 7 days, the employer's admin is told, and permits keep working without it."
  In §22 R4, change "Needed before" from "Phase 6" to "Phase 1" and the mitigation to "lawful basis per data category, notice text and translations reviewed by counsel for India (DPDP Act 2023 and Rules 2025) and the EU (GDPR Art. 6 and 9) before the schema is built."

### R2-05 [blocker] Retention and erasure contradict immutable audit, backups and tenant deletion
- Where: FR-PRV-009, FR-PRV-008, FR-AUD-001 to FR-AUD-003, FR-ONB-013, NFR-AVL-001
- Problem: Audit must hold "what changed" and "before and after values" and can never be deleted (FR-AUD-001 to 003). Any personal or health value that passes through a permit or people change would therefore survive the 30-day and 12-month deletions of FR-PRV-009, against DPDP s.8(7) and GDPR Art. 5(1)(e) and 17. FR-AUD-002 would also keep email-server passwords in clear in an immutable table. Meanwhile FR-ONB-013 deletes a suspended organisation's data after 90 days, which contradicts FR-AUD-003 and the 10-year safety-record period, and nothing says how long backups keep deleted data.
- Change: Add to §15:
  "FR-AUD-005 Audit and access-log records store IDs, field names and non-personal values only. Contact, identity, health and employment-history values never reach audit. A change to one is recorded as 'field X changed by Y at T'. Secrets (email-server passwords, keys) are recorded as 'changed', never as values."
  "FR-AUD-006 The personal-data access log (FR-PRV-008) is readable only by the person it concerns and their employer's admins. It is kept for at least 1 year (default 3 years; changeable per legal entity or agency)."
  Replace FR-AUD-003 with: "Audit records cannot be edited or deleted through any interface. While the organisation is a customer, they outlive the records they describe for the safety-record period. On tenant deletion they are part of the final export (FR-ONB-013)."
  In FR-PRV-009, replace the last clause with: "names and roles on permit records, check-in records and audit actor IDs are kept for the legal entity's safety-record period (default 10 years) as a legal obligation, then pseudonymised."
  In FR-ONB-013, replace "its data is kept for 90 days, then deleted" with: "its data is kept for 90 days, then deleted. Before deletion, admins are offered a full export (permits, incidents, LOTOTO, audit, access log), and the organisation, as controller, keeps its safety records from then on."
  Add to §16: "NFR-AVL-002 Backups are kept for at most 35 days. A deletion ledger (record IDs and deletion time, no content) is re-applied after any restore, before the system reopens."

### R2-06 [major] Identity: one account vs one employer, invitation binding, the sign-in flow and MFA are undefined
- Where: FR-PPL-001, FR-PPL-004, FR-ONB-010, FR-ONB-014, FR-ONB-016, §18 Identity, NFR-SEC-005, §22 R2
- Problem: A person has exactly one employer (FR-PPL-001) yet one account across tenants (FR-PPL-004). Someone who is a client's employee and also an agency's staff needs two employer records under one account, which the §18 `people` model cannot hold. v1 signs in with the OAuth password grant through the API (`app/src/modules/auth/sign-in.service.ts:30`) and finds a user's tenant by matching invite email (`jwt.strategy.ts` `resolveTenantId`). RFC 9700 says the password grant must not be used, and it skips Keycloak's browser flow, so Organizations' identity-first login and per-organisation identity providers, required actions such as email verification, and passkeys never run. Email matching lets whoever controls an address join a tenant, and no MFA is required anywhere, although admins can read health data and ASVS L2 (NFR-SEC-005) expects MFA.
- Change: Add to the §1.5 glossary: "Account: the platform sign-in identity in Keycloak, one per human. Person: an account's record in one employing tenant, with one employer."
  Replace FR-PPL-004 with: "An account may hold person records in several tenants (for example a client's employee who is also an agency's staff). Each person record has one employer (FR-PPL-001), and only that employer's admins manage it. Leaving one employer ends that person record, not the account or the account's other person records."
  Add "FR-ONB-017 An invitation is a single-use link that expires after 7 days. Accepting it links the invitation to the account signed in when the link is opened, once that account has verified the invited email address. Matching an email address at sign-in never grants membership."
  Add "FR-ONB-018 The sign-in page at a slug does not reveal whether an email has an account or belongs to that organisation."
  Replace the first sentence of §18 Identity with: "Identity: one Keycloak realm with Organizations. Web and mobile sign in with OpenID Connect authorisation code and PKCE through Keycloak's login pages (on mobile, through the system browser). The password grant is switched off for every client. The slug passes the organisation hint, and the login theme shows the organisation's logo, name and theme (D14)."
  Add "NFR-SEC-009 Platform admins, support staff, TENANT_ORG_ADMIN and LEGAL_ORG_ADMIN must use a second factor (TOTP or passkey). Anyone else can turn one on, and a legal entity can require it for its people."
  Add to §22 R2's mitigation: "The phase 1 spike proves: one account in two organisations; per-organisation branding on Keycloak's login page; the active organisation in the token; and the mobile code flow."

### R2-09 [major] Client safety records lose agency workers when the engagement ends

### R2-10 [major] The v1 offline store is not fit for personal data or tenant switching
- Where: NFR-OFF-001, §18 Mobile, §23.2 "Kept as is", FR-CRW-002, FR-CRW-003, FR-PRV-006
- Problem: v1 caches API responses, including the workforce directory, in plain expo-sqlite (`mobile/src/lib/offline/database.ts`, `cache.ts`, `mobile/src/lib/workforce/offline.ts`), with no account or tenant key and no expiry, and sign-out clears only tokens (`mobile/src/providers/auth-provider.tsx:45-47`). `sync_queue` has no account or tenant column, so after a tenant switch (FR-ONB-016) queued actions would replay under the other tenant's token, and emergency-subset data would stay on the device after the permit closes. Offline check-in (FR-CRW-002) also cannot apply the certificate block in FR-CRW-003 against live data.
- Change: Replace §18 Mobile with: "Mobile: the offline store is rebuilt, not reused. It is encrypted with a key held in the device keystore (SecureStore) and partitioned by account and tenant. It is wiped on sign-out and after 7 days without a sync. On a tenant switch, cached responses for other tenants are removed; queued actions are kept and sent only while their own tenant is active. Each queued action records account, tenant and permit, and the server refuses one whose tenant does not match the session. The emergency subset and other encrypted fields are never cached offline."
  Add to FR-CRW-002: "Offline, the app checks certificates and insurance against the validity dates downloaded when the permit was issued, refreshed at each sync. The server checks again on sync. A check-in that fails is kept, flagged to the coordinator and receiver, and the person cannot record progress (FR-CRW-005) until it is resolved."
  In §23.2, remove "offline sync" from "Kept as is" and add a row: "Offline store | Plain SQLite response cache and queue, not tied to account or tenant | Encrypted, partitioned by account and tenant, wiped on sign-out | Rebuilt".

### R2-11 [major] Data-protection roles, rights, breach handling and cross-border transfer are missing
- Where: §12, FR-PRV-003, §20 (data residency), §22 D-2
- Problem: The PRD never names the controller (data fiduciary), which is each employer legal entity or agency, or says the platform is a processor, so nobody owns notices, rights requests or breach notification (GDPR Art. 33: 72 hours; DPDP Act s.8(6): the Board and each affected person). Rights stop at view, download and correct (FR-PRV-003), with no erasure, no grievance contact (DPDP s.8(10), s.13) and no deadline. With EU and Indian legal entities (D13), "a single hosting region" moves EU health data out of the EU, or Indian data out of India, with no transfer mechanism, and health data at this scale needs a DPIA (GDPR Art. 35(3)(b)).
- Change: Add §12.4 "Responsibilities and rights":
  "FR-PRV-011 Each employer legal entity or agency is the controller (data fiduciary) for its people's data. The client legal entity is controller for snapshots (FR-AGY-009) and for emergency-subset views. PermitWiseAI is processor under a data processing agreement accepted at onboarding, which names the hosting region and lists sub-processors. The platform is controller only for access-request and account data."
  "FR-PRV-012 Each legal entity and agency records a grievance contact, shown in the notice. A person can request access, correction, erasure and consent withdrawal in the app. Requests go to the employer's admin, are tracked with a status, and must be answered within 30 days. Erasure is refused only for data retained under legal obligation (FR-PRV-009), and the reason is shown."
  "FR-PRV-013 The platform reports a suspected personal-data breach to every affected controller within 24 hours of discovery, giving the data categories, people and tenants affected, so that controllers can meet the GDPR and DPDP deadlines. The platform keeps a breach register."
  "FR-PRV-014 The data processing agreement names the hosting region. If it is outside the EU/EEA, EU customers sign the EU Standard Contractual Clauses, backed by a transfer impact assessment, before go-live. A DPIA covering health data, check-in location and cross-tenant agency sharing is completed before Phase 6 starts."
  In §20, change the residency line to: "Data residency by country (v2 uses a single hosting region, named in the DPA; transfers covered by FR-PRV-014)."

### R2-12 [major] Customer email servers and outside CC addresses open SSRF and data leaks
- Where: FR-ORG-002, FR-LE-003, FR-LE-004, §22 R5, FR-WFD-011, FR-WFD-012, FR-NOT-101
- Problem: Tenant admins can enter any SMTP host and port, and R5 adds a test-send on save. Only ports 25, 465, 587 and 2525 are allowed. TLS (implicit or STARTTLS) with certificate validation is required, and the connect timeout is 10 seconds. A test-send result shows only success or a generic class of failure, never the server's banner or response text."
  Add to FR-WFD-011: "The only personal-data placeholders are people's names. Health, emergency, contact and identity fields are never placeholders."
  Add to FR-WFD-012: "Messages to outside addresses contain only the permit number, title, plant name, step and a link, and the link requires sign-in."

### R2-15 [minor] §18 and §23.2 misstate or omit current facts
- Where: §18 Stack, §23.2 Identity row, §23.2 "Kept as is"
- Problem: §23.2 says v1 takes the tenant "from a token claim". Overall: Not approvable yet from a security and privacy standpoint: five blockers. D16 (shared database, RLS, Keycloak Organizations) is the right direction, but the PRD leaves out the mechanics that decide whether RLS holds at all: an API role that owns no tables and cannot bypass RLS (today everything connects as the superuser), a transaction-local context for requests and jobs, and a column-limited path for agency data. The privacy section rests on a consent flow that contradicts how people are created and does not fit Indian or EU employment law. Deletion cannot coexist with immutable audit that carries values, or with tenant deletion after 90 days. Every fix is additive text. The only change to a decision is a narrow exception to D13 for notice and consent translations, needed for DPDP s.5(3) and s.6(3). With the blockers fixed and the security foundations moved into Phase 1 (R2-13), the architecture is feasible on the current stack, and the Keycloak Organizations spike (R2-06) is the main technical risk left.
